# درگاه بیمار — نسخهٔ پایلوت یک کلینیک

این نسخه ورود حضوری یا درخواست از راه دور، مشخصات و علائم، داروهای اعلامی،
سوابق و پزشکان همکار، رضایت مستقل تبلیغات، کد پیگیری، تصویر مدارک، پرسش پزشک،
پاسخ بیمار و اتصال پذیرش به ویزیت را فراهم می‌کند. خلاصه، بازنمایی اطلاعات
بیمار است؛ تشخیص یا تحلیل خودکار تداخل داروها نیست.

## نصب روی ویندوز موجود

ابتدا سرور را با Ctrl+C متوقف کنید و از PostgreSQL و فایل تنظیمات پشتیبان بگیرید.
فایل تنظیمات یا رمزها را در چت ارسال نکنید. PowerShell را در مسیر پروژه باز کنید:

```powershell
cd "$env:USERPROFILE\4B-MOS"
git pull --ff-only origin main
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m backend.tools.portal_setup
.\.venv\Scripts\python.exe -m backend.tools.portal_access kian
.\.venv\Scripts\python.exe -m backend.tools.portal_access doctor_test
.\.venv\Scripts\python.exe -m backend.tools.release_preflight
.\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

درگاه آزمایشی: `http://127.0.0.1:8000/patient/`

صندوق کارکنان: `http://127.0.0.1:8000/app/portal-inbox.html`

این نشانی‌ها برای همان کامپیوترند. روی گوشی، localhost به خود گوشی اشاره می‌کند.
برای آزمون از دادهٔ ساختگی استفاده کنید. پس از اسکن QR واقعی و روی شبکهٔ عمومی،
نشانی HTTPS معتبر و میزبانی قابل دسترسی لازم است.

ابزار setup کلید جداگانه می‌سازد، آن را چاپ نمی‌کند و در اجرای مجدد همان کلید را
حفظ می‌کند. پشتیبان اولیهٔ تنظیمات با نام `.env.portal-backup.bak` ساخته می‌شود.
پشتیبان تنظیمات **پس از فعال‌سازی** را هم در محل امن نگه دارید؛ پشتیبان اولیه
ممکن است هنوز کلید جدید درگاه را نداشته باشد. با گم‌شدن کلید، درخواست‌ها و مدارک
رمزگذاری‌شده قابل بازیابی نیستند. این فایل‌ها محرمانه‌اند و نباید در مخزن قرار بگیرند.

## آزمون کامل

۱. در مرورگر بیمار فرم چهارمرحله‌ای را پر کنید، رضایت را بخوانید و ارسال کنید.
۲. کد MOS را یادداشت کنید. یک تصویر ساختگی JPG/PNG زیر ۵ مگابایت ارسال کنید.
۳. در مرورگر یا پنجرهٔ دیگر، پزشک دارای دسترسی وارد صندوق شود و کد را انتخاب کند.
۴. خلاصه و اطلاعات ناقص را مرور و پرسش تکمیلی ارسال کند.
۵. بیمار «بررسی وضعیت و پرسش‌های پزشک» را بزند و پاسخ دهد.
۶. پذیرش هویت و وجود پروندهٔ قبلی را بررسی کند. برای بیمار موجود، UUID پرونده
را وارد کند؛ برای فرد جدید کادر را خالی بگذارد. تیک بررسی را بزند و پذیرش را ثبت کند.
۷. شناسهٔ ویزیت را در کنسول پذیرش و پزشک‌یار بارگذاری کنید. شرح‌حال نهایی و
رضایت‌های درمان/ضبط را جداگانه طبق روند موجود ثبت کنید؛ رضایت درگاه جای آنها نیست.
۸. خروج هر دو صفحه، پاک‌شدن اطلاعات و رد دسترسی بدون مجوز صندوق را بررسی کنید.

دسترسی صندوق با فرمان زیر لغو می‌شود:

```powershell
.\.venv\Scripts\python.exe -m backend.tools.portal_access doctor_test --revoke
```

## اتصال به سایت کلینیک و QR

این کد در سایت فقط یک دکمهٔ ورود می‌سازد؛ اطلاعات پزشکی در WordPress وارد نمی‌شود:

```html
<a href="https://PATIENT-HOST/patient/">پذیرش آنلاین و ارسال مدارک</a>
```

`PATIENT-HOST` جایگزین آزمایشی است، نه نشانی فعال. پس از آماده‌شدن میزبانی HTTPS،
فرمان زیر origin را تنظیم و QR همان درگاه را ایجاد می‌کند:

```powershell
.\.venv\Scripts\python.exe -m backend.tools.portal_setup --origin https://PATIENT-HOST --qr patient-portal-qr.png
```

سرور را پس از تغییر origin راه‌اندازی مجدد کنید. نام دامنهٔ درخواست و origin باید
یکسان باشند. پراکسی باید HTTPS را خاتمه دهد، اندازهٔ بدنه و نرخ درخواست را محدود
کند و فقط مسیرهای لازم را به برنامه برساند؛ صندوق، API کارکنان، login و کنسول
از شبکهٔ عمومی محدود شوند. هیچ قابلیت ضبط یا API کارکنان را صرفاً برای QR عمومی نکنید.
IP پراکسی در محدودیت داخلی مشترک محسوب می‌شود؛ forwarded headers دلخواه اعتماد نمی‌شوند.

## حدود این انتشار

- یک نصب برای یک کلینیک؛ اشتراک چند کلینیک در یک پایگاه داده هنوز فعال نیست.
- نشست بیمار ۱۲ ساعته و موقت است. کد پیگیری مجوز دیدن پرونده نیست. پیامک/OTP،
  حساب دائمی بیمار و بازیابی از دستگاه دیگر هنوز اضافه نشده‌اند.
- مدارک صرفاً تصویر JPG/PNG هستند و پس از رمزگشایی و بازنویسی تصویر ذخیره می‌شوند؛
  PDF، DICOM، فیلم و پردازش/OCR خودکار پشتیبانی نمی‌شوند.
- پرسش‌های تکمیلی بالینی توسط پزشک ارسال می‌شوند. فرم، راهنمای مرتبط با ناحیه را
  نشان می‌دهد، اما دستیار تشخیصی یا قواعد خودکار تداخل/منع مصرف در این مسیر فعال نیست.
- پزشکان همکار فعلاً اطلاعات اعلامی بیمارند؛ اشتراک واقعی بین متخصصان و کلینیک‌ها
  نیازمند هویت تأییدشده، مجوز بیمار، مدل مالکیت کلینیک و کنترل دسترسی جداگانه است.
- پس‌گرفتن درخواست، آن را می‌بندد؛ سوابق قبلی حذف یا ویزیت ایجادشده لغو نمی‌شود.
- زمان نگهداری، پاسخ‌گویی به درخواست اصلاح/حذف و دسترسی اضطراری باید پیش از پذیرش
  دادهٔ واقعی توسط مسئول کلینیک تعیین شود. فعال‌کردن پایلوت به‌تنهایی تأیید انتشار عمومی نیست.
