# آزمون اتصال هسته‌های تخصصی به موتور یکپارچه‌سازی

این مرحله روی نسخه تحویل‌شده مسیر C ساخته شده است. هدف آن اجرای کد واقعی
دو تولیدکننده در محیط آزمایشی موقت و بررسی مرز مسئولیت‌ها است. هیچ کد هسته
تخصصی، دانش Draft، Router، تنظیمات یا migration آن‌ها به شاخه تحویل کپی یا
ادغام نمی‌شود. API عملیاتی نیز Adapter تازه‌ای ثبت نمی‌کند.

## ابزار ترکیب موقت و منشأ کد

فایل `backend/compatibility/specialist_pins.json` نسخه تولیدکننده و Git blob hash
تک‌تک فایل‌های مجاز را نگه می‌دارد. ابزار
`python -m backend.tools.compose_clinical_handoff` ابتدا تمام ورودی‌ها را بررسی
می‌کند، سپس یک پوشه خروجی تازه می‌سازد:

- HEAD هر checkout تخصصی باید دقیقاً با SHA ثبت‌شده برابر باشد. نسخه Integration
  می‌تواند فرزند مبنای مشخص‌شده باشد؛ SHA واقعی آن در رسید ثبت می‌شود.
- محتوای تمام فایل‌های تخصصی باید با hash ثابت مطابقت داشته باشد. مسیر خارج
  از فهرست، فایل مفقود، symlink، traversal و بازنویسی فایل Integration رد می‌شوند.
- Router، config، migration و workflow تولیدکننده وارد ترکیب نمی‌شوند. فایل‌های
  schema، سرویس، مدل و route فعلی Integration با همان بایت‌ها حفظ می‌شوند.
- خروجی باید تازه و خارج از ورودی‌ها باشد. خطای پیش‌بررسی خروجی نیمه‌کاره ایجاد
  نمی‌کند و خطای کپی، فقط خروجی موقتی همان اجرا را پاک می‌کند.
- `.git`، cache، فایل `.env`، پایگاه داده محلی و checkoutهای داخل
  `.handoff-sources` وارد محیط تست نمی‌شوند. اندازه ورودی محدود است.

گزینه `--allow-exported-sources` فقط برای بازسازی محلی با Connector است؛ hash
همه فایل‌های تخصصی همچنان اجباری است، اما `git_revisions_verified=false` و
`integration_revision=null` ثبت می‌شود. این حالت ادعای بررسی HEAD گیت نمی‌کند.
CI گزینه یادشده را استفاده نمی‌کند و checkoutهای واقعی را بررسی می‌کند.

این ابزار merge یا cherry-pick انجام نمی‌دهد و به سرویس خارجی متصل نمی‌شود.
رسید آن فقط نسخه‌ها، مسیر نسبی فایل کد، hash، تعداد و دامنه آزمون را دارد؛
متن پزشکی، شناسه بیمار، URL منبع و متن exception در رسید یا خطای عمومی نمی‌آیند.

## نتیجه تصویربرداری

کد واقعی تولیدکننده یک MRI سه‌برشی کاملاً ساختگی می‌سازد، Study/Series را با
فهرست موردانتظار بررسی می‌کند و نتیجه را به گزارش موجود متصل می‌کند. Adapter
مقدار و مرجع observation را حفظ می‌کند و یافته پزشکی تازه‌ای از metadata نمی‌سازد.

تست‌ها این موارد را بررسی می‌کنند: پذیرش توسط Schema فعلی، حفظ مقدار و origin،
رد نسخه/هش گزارش یا زمینه ناسازگار، رد Series نامنطبق و Study نامعتبر، تغییر
اثر انگشت component در تغییر sidecar، جلوگیری از حذف بی‌صدای منبع اضافی و
رفتار واقعی API و Run ذخیره‌شده پس از تغییر وابستگی.

`data_ready` تأیید پزشک یا Clinical Clearance نیست. نبود نهایی‌سازی منتسب به
پزشک، یافته را unreviewed و خلاصه را blocked نگه می‌دارد. حتی در گزارش تأییدشده،
`dicom_identity_verified=false` باقی می‌ماند؛ کنترل metadata و اتصال گزارش،
هویت بیمار یا کیفیت بالینی تصویر را اثبات نمی‌کند. متناظرشدن یک Volume با یک
گزارش، محدودیت فعلی Adapter تخصصی است و بی‌صدا به چند مطالعه تعمیم داده نمی‌شود.

## نتیجه ارتوپدی و مرز دانش Draft

Schema واقعی تولیدکننده و نمونه نگه‌داری‌شده آن مستقیماً اعتبارسنجی می‌شوند؛
Schema ارتوپدی در مسیر C دوباره پیاده‌سازی نشده است. تولید مجدد با کد واقعی
باید دقیقاً همان نمونه و hash نتیجه را بسازد.

نمونه شامل ۲۷ ارجاع دانش Draft، صفر fact تأییدشده و ۱۷ پرسش متناسب با ورودی
ساختگی است. تعداد پرسش‌های انتخاب‌شده با تعداد پرسش‌های موجود در بسته تفاوت دارد.
این خروجی از `CoreOutput` و `KnowledgeReference` تأییدشده متمایز و برای انتقال
خودکار به آن‌ها رد می‌شود. گزارش فنی وضعیت `draft_quarantined` می‌دهد؛ این عنوان
به معنای ایجاد Registry یا صف قرنطینه تازه در پایگاه داده نیست.

`context_sha256` ارتوپدی از شرح ساختاریافته حداقلی آن هسته ساخته می‌شود و برابر
هش پرونده نهایی‌شده Integration نیست. `source_ref` یا پاسخ `state=confirmed`
به‌تنهایی شناسه نسخه/هش رکورد و بازبینی احراز هویت‌شده پزشک را فراهم نمی‌کند.
بنابراین هیچ نگاشت خودکار از متن آزاد پرونده یا پاسخ تأییدنشده انجام نمی‌شود.
اتصال واقعی این دامنه‌ها به projection صریح، قابل‌بازبینی و دارای منشأ سمت سرور
نیاز دارد. hash منبع ارتوپدی نیز hash metadata ارجاع است، نه hash بایت مقاله.

## اجرای مستقل و CI

نیازمندی اختیاری `backend/requirements-clinical-handoff.txt` شامل pydicom و
jsonschema است؛ MONAI، مدل MRI، شبکه بیزی یا سرویس پولی لازم نیست. این فایل
نیازمندی عملیاتی Backend را تغییر نمی‌دهد.

از checkout Integration و دو checkout تخصصی با SHAهای جدول بالا:

```sh
python -m pip install -r backend/requirements.txt -r backend/requirements-dev.txt -r backend/requirements-clinical-handoff.txt
python -m backend.tools.compose_clinical_handoff --imaging-root ../imaging --orthopedic-root ../orthopedic --output ../clinical-handoff-composition
cd ../clinical-handoff-composition
python -m pytest backend/tests backend/compatibility -q
python -m backend.tools.clinical_handoff_report
```

Workflow اختصاصی روی Python 3.12 و 3.14 ابتدا خود پیشنهاد Integration را تست
می‌کند، سپس در پوشه موقت تست‌های ترکیبی را با pytest معمولی اجرا می‌کند. رسیدهای
دارای hash به‌عنوان artifact نگه‌داری می‌شوند؛ کد تخصصی یا بسته دانش به شاخه
تحویل افزوده نمی‌شود. نبود وابستگی تخصصی در تست opt-in خطاست، نه skip ظاهراً موفق.

در تست واحد مرز مصرف‌کننده، validator ساختگیِ صریح برای آزمودن قواعد مستقل
مصرف‌کننده به‌کار می‌رود. اعتبار واقعی Schema تولیدکننده با jsonschema واقعی
و کد واقعی آن، جداگانه در تست ترکیبی بررسی می‌شود؛ این دو نتیجه یکی فرض نمی‌شوند.
تمام رکوردها ساختگی و SQLite تست در حافظه یا فایل موقت است.

## محدودیت و اولویت بعدی

این مرحله سازگاری نرم‌افزاری را می‌آزماید و مجوز واردکردن کد PRهای ادغام‌نشده،
تأیید مستقل دانش یا فعال‌سازی بالینی نیست. بازبینی اختصاصی مدل، اتصال احراز
هویت‌شده مطالعه به ویزیت، مدیریت کلید و دسترسی DICOM و projection معتبر زمینه
ارتوپدی هنوز نیازمند قرارداد و پیاده‌سازی هماهنگ دو مسیر تخصصی‌اند. هیچ migration
تازه، اتصال به کلینیک، deploy، Force Push یا ادغام به main انجام نشده است.
