# تحویل مسیر C: یکپارچه‌سازی هوش بالینی

این سند مرز کار انجام‌شده روی PR موجود، قراردادهای قابل‌استفاده و ورودی‌های لازم از دو مسیر تخصصی را ثبت می‌کند. خروجی این موتور یک نمای قابل‌بازبینی برای پزشک است؛ تشخیص، رتبه‌بندی درمان، نسخه یا مجوز انجام درمان تولید نمی‌کند.

## مبنای واقعی بررسی مخزن

در بررسی آغاز مأموریت در ۱۹ اکتبر ۲۰۲۶، مبنای `main` کامیت `bc6fb3f15825d6eaccaa45503ad61a432baf1c5b` بود. ساختار Backend شامل FastAPI، SQLAlchemy، Pydantic، سرویس‌های زمینه بالینی، Registry دانش، Safety و Physician Copilot بود؛ وجود این سرویس‌ها به معنای اعتبارسنجی بالینی هسته‌های تخصصی نیست.

بخش عمده قرارداد v1، موتور ترکیب، ذخیره Run، بازبینی پزشک، Audit و migration پیشنهادی از قبل در PR شماره ۴۴ وجود داشت. این نوبت آن‌ها را بررسی و تکمیل می‌کند؛ ادعای ایجاد دوباره تمام آن زیرساخت مطرح نیست. هیچ تغییر PR شماره ۴۳ به‌صورت خودکار ادغام نشده و هیچ شاخه تخصصی بازنویسی نشده است.

## استفاده مجدد از اجزای موجود

- نسخه و هش زمینه بالینی از `ClinicalContextSnapshotRead` و ورودی‌های نهایی‌شده گرفته می‌شود. شناسه، نسخه، هش، زمان نهایی‌سازی و هویت نهایی‌کننده رکورد حفظ می‌شوند.
- مقدار ساختاریافته مشاهده بر پایه `ParaclinicalObservationInput` است. قرارداد انتقالِ یکپارچه‌سازی اعتبارسنجی سخت‌گیرانه‌تری روی همین شکل داده اعمال می‌کند؛ API اصلی ثبت مشاهده بازنویسی نشده است.
- اعتبار دانش از Medical Knowledge Registry بررسی می‌شود. عبارت `approved` در payload مدل، جای بررسی سمت سرور را نمی‌گیرد. ارتباط دانش با بیمار نیز صرفاً با ارجاع برقرار می‌شود و `applicability=not_assessed` باقی می‌ماند.
- ارزیابی Safety از سرویس موجود و با هش زمینه و مجموعه قواعد فعلی کنترل می‌شود. یافته مدل و امتیاز احتمالاتی نمی‌توانند هشدار را حذف یا آن را به Clinical Clearance تبدیل کنند.
- Physician Copilot موجود منبع زمینه و وابستگی‌ها باقی می‌ماند. خروجی مستقل یکپارچه‌سازی API اصلی آن را تغییر نمی‌دهد.
- ثبت بازبینی و Audit به مسیر احراز هویت‌شده موجود متکی است. نقش فعال پزشک در سمت سرور بررسی می‌شود؛ نهایی‌بودن رکورد توسط مدیر به‌تنهایی تأیید پزشک محسوب نمی‌شود.

قرارداد عمومی موجود و سیاست نسخه‌بندی در [سند قرارداد v1](contracts/unified-clinical-data-v1.md) توضیح داده شده است. این شکل‌ها از مفاهیم Observation و ImagingStudy الهام گرفته‌اند؛ پیاده‌سازی یا ادعای انطباق رسمی HL7 FHIR نیستند.

## اصلاحات قرارداد پیش‌نویس و موتور

موتور اصلاح‌شده با شناسه `clinical-integration-1.0.1` خروجی می‌دهد. تغییر نسخه موتور سبب می‌شود Run قدیمی بدون بررسی مجدد وابستگی‌ها جاری تلقی نشود.

سه اشکال بررسی‌شده در قرارداد و ترکیب اصلاح می‌شوند:

1. فیلد ناشناخته داخل خود مشاهده دیگر بی‌صدا حذف نمی‌شود؛ از جمله فیلدهای اضافه وضعیت تأیید یا محدودیت کیفیت که تولیدکننده بخواهد خارج از قرارداد بفرستد. تولیدکننده باید شکل نسخه منتشرشده را رعایت کند.
2. حالت‌های ناسازگار تأیید در Pydantic رد می‌شوند. `origin=model` نمی‌تواند همراه `confirmed_source`، تأیید پزشک یا قابلیت استفاده به‌عنوان یافته تأییدشده باشد. مجموعه‌های confirmed و unreviewed نیز همین قاعده را اعمال می‌کنند.
3. حذف جزئی یا کامل منابع ورودی توسط Adapter قابل‌مشاهده و بازدارنده است. `incomplete_core_coverage` منابع حذف‌شده را مشخص می‌کند؛ خروجی خالی به‌عنوان خلاصه آماده تأیید معرفی نمی‌شود. منابع خام در خروجی حفظ می‌شوند.

شماره قرارداد هسته در این اصلاحات `1.0.0` باقی می‌ماند، زیرا هنوز پیش‌نویس PR باز است. این اصلاح سخت‌گیرانه می‌تواند payload قبلاً پذیرفته‌شده اما خارج از شکل مستند را رد کند؛ تولیدکننده‌های دو مسیر باید JSON Schema به‌روزشده را پیش از اتصال اجرا کنند. پس از تثبیت و انتشار قرارداد، چنین تغییر پذیرشی باید نسخه و سیاست مهاجرت مشخص داشته باشد. قرارداد JSON هسته در [این فایل](contracts/unified-clinical-core-output-1.0.0.schema.json) نگهداری می‌شود.

## چهار مرحله مجزای مسئولیت بالینی

| مرحله | معنی و حد اختیار |
| --- | --- |
| Raw Observation | مقدار ثبت‌شده یا مرجع منبع است. صرف حضور در پرونده یا پاسخ API به معنی تأیید پزشک نیست. |
| AI-Generated Finding | ادعای مدل با نسخه مدل، منابع، هش زمینه، زمان و محدودیت‌ها است. حتی confidence بالا آن را تأییدشده نمی‌کند. |
| Clinician-Verified Finding | در این نسخه، برای passthrough رکورد فقط مقدار دقیق منبع با نهایی‌سازی معتبر منتسب به پزشک پذیرفته می‌شود. تأیید جداگانه خودِ خروجی مدل هنوز نیازمند جریان تخصصی معتبر است. |
| Final Clinical Decision | تصمیم مسئولانه پزشک در جریان تصمیم بالینی موجود ثبت می‌شود. تأیید خلاصه یکپارچه‌سازی، مشاهده خام یا خروجی مدل را به تصمیم نهایی یا مجوز درمان تبدیل نمی‌کند. |

نام `confirmed_source` محدوده تأیید منبع را مشخص می‌کند؛ تأیید مستقل هویت DICOM، کیفیت تصویر، صحت الگوریتم یا کاربرد یک یافته برای یک درمان خاص را تضمین نمی‌کند. `approve_summary` نیز فقط به همان خلاصه و هش مشخص مربوط است.

## قرارداد مستقل موتور تصمیم و Mockها

در [clinical_decision_exchange.py](../backend/app/schemas/clinical_decision_exchange.py)، `DecisionModelResult` و `DecisionModelReference` به‌صورت افزوده روی همان مرجع‌های منبع و نسخه مدل تعریف شده‌اند. `DecisionAdapter` و گردآوری محدودشده در [decision.py](../backend/app/services/clinical_integration/decision.py) قرار دارند.

نسخه اول این تبادل فقط امتیازهای ساختاریافته پژوهشی یا کیفیت ورودی را می‌پذیرد. تشخیص، گزینه درمان رتبه‌بندی‌شده و دستور درمان در قرارداد آن وجود ندارد. خروجی تولیدکننده همیشه `review_status=unverified` و `usable_as_confirmed_finding=false` است. فیلد ادعایی تأیید پزشک یا Clinical Clearance پذیرفته نمی‌شود.

گردآوری، شناسه ویزیت، هش زمینه، نسخه و artifact مدل، نسخه و هش منابع، زمان تولید، انقضا و دانشِ دقیقاً منطبق با ارجاع‌های جاری Registry ارائه‌شده از سمت سرور را کنترل می‌کند. محدودیت ۲۴ ساعت برای عمر خروجی تصمیم، یک پنجره اداری بازبینی است و قاعده اعتبار بالینی محسوب نمی‌شود. خطا با کد محدود و بدون متن exception، اطلاعات بیمار یا URL دارای توکن بازگردانده می‌شود. نبود مدل، خطا، خروجی نامعتبر و خروجی منقضی حالات مجزا هستند.

`MockOrthopedicAdapter`، `MockImagingAdapter` و `MockDecisionAdapter` تنها fixture ساختگی ثابت `synthetic_core_input()` را می‌پذیرند؛ دو Mock هسته زیرمجموعه دقیق همان ورودی را نیز برای جداسازی ورودی هسته قبول می‌کنند. عوض‌کردن مقدار، شناسه، نسخه یا هش، حتی با شناسه‌ای که ظاهر ساختگی دارد، رد می‌شود. این Mockها در API یا تنظیمات عملیاتی ثبت نشده‌اند. هیچ مدل MRI، MONAI، شبکه بیزی یا سرویس پولی لازم ندارند.

## خروجی مستقل فقط‌خواندنی

مسیر افزوده `GET /api/v1/visits/{visit_id}/clinical-intelligence` برای نقش‌های مجاز، Snapshot را بدون ایجاد Run، ثبت تأیید یا نوشتن رکورد بالینی تولید می‌کند. این مسیر زیر پرچم پیش‌نمایش موجود `CLINICAL_INTEGRATION_ENABLED` قرار می‌گیرد که پیش‌فرض آن غیرفعال است.

پاسخ، `DecisionSupportResult` موجود را با مرجع روشن ارزیابی Safety، فهرست وضعیت بازبینی تصویربرداری و مرجع موتور تصمیم همراه می‌کند. تا زمان ثبت Adapter معتبر تصمیم، مرجع تصمیم صریحاً missing است. نبود تصویربرداری باید به‌صورت `imaging_unavailable` قابل‌تشخیص باشد؛ نبود یا خرابی وابستگی نباید به اعلام موفقیت بالینی تبدیل شود. وضعیت تأیید گزارش محلی و تأیید خودِ خروجی مدل دو مفهوم جدا هستند.

هش معنایی Snapshot از serialization کانونی ساخته می‌شود تا تکرار همان داده و وابستگی صرفاً به‌دلیل زمان ترکیب هش دیگری نسازد. زمان‌های موقتی فرایند ترکیب از محتوای این هش کنار گذاشته می‌شوند؛ زمان و انقضای واقعی خروجی مدل همچنان در کنترل اعتبار اهمیت دارند. تغییر منبع، نسخه مدل، دانش یا قواعد وابسته باید نتیجه را برای بررسی مجدد متمایز کند. SHA-256 امضای دیجیتال و تضمین صحت بالینی نیست.

خواندنی‌بودن این API، مسیر بازبینی دارای Audit را جایگزین نمی‌کند. ایجاد شواهد پایدار و ثبت بازبینی واقعی از مسیرهای Run و Review موجود انجام می‌شود. Manifest یا لاگ فنی عمومی محل نگهداری متن حساس پرونده، مشخصات شناسایی بیمار یا لینک توکن‌دار نیست.

## اعتبارسنجی، محدودیت و اولویت بعدی

تست‌های اضافه، اعتبار قرارداد تصمیم، جلوگیری از تأیید خودکار، تطبیق زمینه/منبع/مدل/دانش، انقضا، رفتار خطا و محافظ Mock را با داده ساختگی بررسی می‌کنند. تست‌های قرارداد و API یکپارچه‌سازی نیز باید همراه همین تغییرات اجرا شوند. نتیجه تست‌های نسخه قبلی PR یا نتیجه skip به‌عنوان موفقیت نسخه جدید گزارش نمی‌شود؛ گزارش اجرای نهایی و checks باید با SHA تحویلی PR تطبیق داده شوند.

این نوبت migration جدیدی برای GET و تبادل تصمیم اضافه نمی‌کند. migration پیشنهادی موجود در مبنای PR شماره ۴۴، مجوز اجرا روی پایگاه داده کلینیک نیست. هیچ داده واقعی بیمار، اتصال عملیاتی، استقرار، Force Push یا ادغام به main برای این کار لازم نیست.

اولویت بعدی، قرارداد و حمل معتبر منشأ واقعی مطالعه تصویربرداری و وضعیت بازبینی تخصصی احراز هویت‌شده است: هویت مطالعه، دسترسی و اتصال به ویزیت، کیفیت، نسخه مدل و رویدادهای بررسی/رد/ابطال باید از داده مرجع معتبر دریافت شوند. پس از آن می‌توان Adapter واقعی را با همان تست‌های قرارداد جایگزین کرد. تحلیل تصویر، استنتاج ارتوپدی و اعتبارسنجی بالینی مدل‌ها مسئولیت هسته‌های تخصصی باقی می‌ماند.
