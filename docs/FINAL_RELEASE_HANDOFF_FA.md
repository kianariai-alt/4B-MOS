# بسته نهایی تحویل مهندسی 4B-MOS

این سند، تحویل **کد و فرآیند استقرار پایلوت کنترل‌شده** است؛ نه اعلام نصب
روی سرور واقعی، نه تأیید درمان و نه شروع کار با پرونده‌های واقعی بیمار.
تا تکمیل تأییدهای انسانی و استقرار در محیط کلینیک، وضعیت عملیاتی
`NOT_LIVE` است.

## محدوده تحویل کد

- ثبت بالینی، ویزیت، مواد و رهگیری جلسات و اصلاحات append-only؛
- زمینه بالینی، قواعد ایمنی، مرور پزشک و پیشنهاد چندگزینه‌ای قابل‌بررسی؛
- تصمیم مستقل پزشک، نتیجه درمان و مرور داده‌های بیماران مشابه؛
- Governance پروتکل، انتشار کنترل‌شده، بازیابی و زنجیره نسخه‌ها؛
- Gate آمادگی محیط، هفت تأیید دستی، Launch Package و تصمیم مستقل Admin؛
- ثبت‌نام ویزیت با سقف، تصمیم پزشک و ارجاع سند رضایت، توقف پایلوت؛
- گزارش شواهد بدون ادعای اثربخشی یا مجوز خودکار گسترش؛
- کنسول فارسی، API، migration و آزمون‌های CI با داده مصنوعی.

## اجرای استقرار توسط مسئول فنی کلینیک

۱. نسخه release را با commit و digest تصویر ثبت و روی staging مستقل نگهداری کنید.
هیچ داده واقعی بیمار یا secret را در GitHub، لاگ، چت یا خروجی CI قرار ندهید.

۲. PostgreSQL مخصوص پایلوت، نسخه پشتیبان رمزنگاری‌شده، بازیابی آزمایش‌شده،
HTTPS، دسترسی محدود، هشدار رخداد، برنامه قطعی برق/شبکه و ثبت محرمانه داده را
با مسئول نام‌دار آماده کنید. نسخه قبلی را پیش از migration متوقف کنید.

۳. در پنجره نگهداری، تصویر مورد تأیید را یک‌بار migrate کنید:

```sh
python -m alembic upgrade head
python -m alembic heads
python -m backend.tools.release_preflight
python -m backend.tools.pilot_readiness --format json
```

Revision مورد انتظار این تحویل `b6e9c2d4a731` است. در production از
`ENVIRONMENT=production`، `DEBUG=false`، `BOOTSTRAP_ENABLED=false`
و کلید تصادفی قوی محافظت‌شده استفاده کنید. در **محیط مجزای پایلوت**،
پس از تأیید همه مسیرهای توقف و مراقبت، `PILOT_ENFORCEMENT_ENABLED=true`
قرار دهید. این گزینه را بدون طرح جداسازی روی کل کلینیک روشن نکنید.

۴. تیم مستقل پزشکی/حقوقی/امنیت، هفت Manual Gate را با مدرک واقعی، امضا/تأیید
مجاز و مرور مستقل ثبت کند. خودکار بودن checklist، جای این تصمیم‌ها را نمی‌گیرد.

۵. Admin نخست Launch Package را freeze کند؛ Admin مستقل بر مبنای بسته و
scope زمانی/سقف/پروتکل‌های فعال تصمیم `authorize` یا `hold` بگیرد.
در تصمیم `hold` پایلوت قابل اجرا نیست.

۶. پزشک برای هر ویزیت، سند معتبر رضایت بیمار را خارج از سامانه بررسی کند؛
تصمیم بالینی فعلی و پروتکل دقیق را ثبت کند؛ سپس ویزیت را در پایلوت وارد کند.
این ثبت‌نام به‌تنهایی مجوز درمان فردی نیست.

۷. مسیر STOP را با داده آزمایشی و سناریوی شکست ارتباط/تداخل هم‌زمان تمرین
کنید. پس از STOP، مراقبت ضروری بیمار و مستندسازی واجب را مطابق رویه بالینی
مستقل ادامه دهید؛ برای شروع پایلوت جدید یک Release تازه لازم است.

۸. در پایان دوره، گزارش پذیرش را همراه شواهد پیگیری، عوارض، فقدان داده‌ها و
نتیجه مرور مستقل پزشکان بررسی و جداگانه تصویب یا رد کنید. سیستم صرفاً
پرونده شواهد ارائه می‌دهد؛ اثربخشی و گسترش را تصویب نمی‌کند.

## معیار پایان کار مهندسی در این مخزن

PR ادغام‌شده روی `main`، همه jobهای Backend/SQLite/Python 3.12 و 3.14،
PostgreSQL 18، Production Container و قرارداد OpenAPI سبز؛ migration head
به‌روز؛ نبود داده واقعی در تست‌ها؛ و مستند راه‌اندازی و توقف در همین مخزن.

## مواردی که از طریق GitHub قابل ادعای انجام‌شدن نیستند

استقرار واقعی روی سرور کلینیک، اثبات اصالت رضایت بیمار، بازبینی پزشکی نهایی،
امنیت شبکه واقعی، backup/restore در زیرساخت واقعی، تست بار و failover، پذیرش
کاربران کلینیک، قراردادهای پردازش داده، مانیتورینگ ۲۴ساعته و صدور مجوز
رگولاتوری. برای هیچ‌کدام داده یا تأیید واقعی در این repository وجود ندارد.
